# GraalVM 25.4

`2026-10-03`

CrucibleVM is based on the tag `vm-25.3.4.1`.
The 25.3 release branch has no commits beyond it, and the 25.4 line, tag `vm-25.4.4.1.1` from 2026-09-17, is 390 commits ahead with the JDK `ce-25.0.4.1.1+1-jvmci-25.4-b23`.
The branch `crucible/upgrade-25.4` merges that tag.

## The Merge

Nine files changed on both sides.
Four of them conflicted:

- _common.json_, _JVMCIVersionCheck.java_, and _ci_includes/publish-javadoc.jsonnet_ take 25.4's version.
- _HostedConfiguration.java_ takes 25.4's version: 25.4 makes the object layout with identity hash codes added on demand the default itself, so this tree's own default for `-H:+OptionalIdentityHashCodes` is removed from _SubstrateOptions.java_.

The tree then builds and passes `mx checkstyle`.

## What Broke

`mx helloworld` builds with assertions on, and the image failed in `ForeignCallNode.setBci` while lowering an exact array copy.
The exact array copy snippets of `-H:InlineExactArraycopy` called the stub for each element kind through a node intrinsic of `ForeignCallNode`.
An intrinsic takes the bytecode index of the enclosing non-intrinsic method when the snippet is parsed, here −6, and instantiating the snippet then sets the index of the copy it replaces, which the assertion refuses.
The same code is in the 25.3 tree; builds without assertions overwrite the index and run correctly.

The stubs are now called through `SubstrateExactArrayCopyCallNode`, in the shape of the generic copy call: it picks the stub for its element kind when it is lowered, after frame states are assigned, and takes the index of the copy once.
Its calls appear only after analysis, so the nine stubs are analysis roots, like the generic copy next to them in `NativeImageGenerator`.

## What It Is Worth

Fourteen Renaissance benchmarks, five rounds each, all binaries timed in the same session at `-O3`: the 25.3 binary from its recording, a new recording with the 25.4 instrumented binary and the binary built from it, and Oracle's profile-guided binary.

| | against Oracle's binary |
| --- | --- |
| 25.3 | 0.944 |
| 25.4 | 0.945 |
| 25.4 with `-H:LargeArrayThreshold=520000` | 0.929 |

25.4 is level with 25.3 over the fourteen.
fj-kmeans, philosophers, scala-kmeans, future-genetic, reactors, and finagle-http are 2 to 5% faster; scala-doku, mnemonics, and rx-scrabble are 2 to 4% slower.
The large-array threshold costs scala-kmeans nothing on 25.4, where it cost 1.7% on 25.3.

A 25.4 binary built from the 25.3 recording separates the recording from the compiler:

| median, ms | Oracle | 25.3 | 25.4 | 25.4 from the 25.3 recording |
| --- | --- | --- | --- | --- |
| scala-doku | 1240 | 1057 | 1076 | 1078 |
| mnemonics | 1832 | 1603 | 1668 | 1781 |

scala-doku's 2% is 25.4's own.
On mnemonics the old recording is 11% slower on 25.4 and the new one 4%: the lead there rests on `wordCode` being inlined into its caller, and 25.4 tips that decision the other way more often.

akka-uct runs at one of two speeds, about 10.7 s and 12.5 to 13 s an iteration, and in the five rounds of the comparison 25.4 had happened never to run fast.
Over eight more rounds, 25.3 and 25.4 each ran fast in four, with means of 11,576 and 11,773 ms against Oracle's 13,907.

## What Is Left

- Making `wordCode`'s inlining on mnemonics independent of small changes to the compiler and the class library.
- scala-doku's 2% on 25.4, which is in the compiler or the class library, not in the recording.
